Security model  /  Development scope

Claims should follow evidence.

This page separates the present prototype from the production architecture we intend to validate.

Implemented now
A static browser interface. Text stays in page memory; selected files are identified by name and size but are not read or uploaded. No backend is connected.
Not implemented
Cryptographic operations, ciphertext storage, one-time retrieval, authentication, notifications, automated deletion, rate limiting, and bot protection.
Planned design
Browser-generated AES-GCM keys, authenticated encryption, URL-fragment key delivery, short-lived ciphertext, atomic read-and-delete operations, strict content security policy, and minimal operational logging.
Threat boundaries
A future zero-knowledge design would reduce server-side exposure but would not protect a compromised browser, malicious extension, recipient screenshot, unsafe endpoint, copied link, or sender mistake.
Verification gates
Before launch: independent cryptographic review, abuse analysis, dependency audit, deletion tests, recovery exercises, CSP verification, logging review, and documented incident response.
Disclosure
Report a potential issue privately to security@privacylock.io. Do not include real credentials or access data you do not own.
